### Account boundary clarified by the user

The backend is used only when the player is signed into an account. Signed-out play is entirely frontend/local: no anonymous server profile, guest session, background save requests or cloud polling. The player can explicitly initiate sign-in/account recovery; those authentication requests are the entry into account features.

After sign-in, enable cloud synchronization and account/social features for selected towns. Gameplay and immediate saves still run locally, including while offline. Signing out or losing authentication stops background backend work and invalidates in-flight account responses while preserving local progress. Network availability alone never enables backend use, and the three-town limit applies to cloud towns owned by the account.

The user further clarified that **signed-out/local-only play has exactly one town slot**. The **three-town save slots are available only to signed-in accounts**; do not offer multiple local-only towns or a three-slot selector while signed out. Signing in can attach the existing local town to an available account slot with confirmation. Account-full handling must preserve that local town. Signing out must not delete account saves or cached progress merely to enforce the single local-only slot. A temporary network outage is distinct from signing out: signed-in players retain offline gameplay and pending sync.

### Sync details that need explicit tests

These are implementation consequences of the requested design, rather than extra gameplay scope:

- Signed-out startup, play, purchases, saves, resume and reconnect make no backend requests. Explicit sign-in enables account features; sign-out/session expiry stops them without blocking local play or losing local saves.
- Local-only play offers one town slot; signing in unlocks up to three independent account town slots. Creating/importing another local-only save must not create an extra slot or silently overwrite the existing town. Cover sign-in attachment, full accounts and sign-out without deleting saved progress.
- A successful upload must clear only the local changes included in that upload. If another local save happens while HTTP is pending, keep the newer state dirty.
- Apply a download only if that town has not become dirty since the request began. Switching accounts/towns must invalidate stale responses without discarding local progress.
- Resolve against the cloud revision actually shown in the comparison. If another device updates it while the dialog is open, refresh the comparison rather than silently overwriting unseen progress.
- Recover a lost upload acknowledgment at the save level. Do not introduce another gameplay action journal, and do not claim “Cloud saved” until acceptance is established.
- Persist profile data and its dirty metadata coherently so a tab/app crash cannot leave changed progress incorrectly marked clean.
- Migrate existing local saves to town UUIDs without resetting progress. Define how old manual backups acquire or preserve identity. Name collisions must trigger a rename, not identity matching or save merging. The unused backend schema can be replaced instead of migrated.
- Town deletion must not cause another device to silently re-upload and resurrect the deleted cloud town; preserve its local copy and request an explicit attachment decision.

## Concrete defects and rule drift in the current branch

1. **Hard run expiry violates the permanent gameplay rule.** `PuzzleService.php` sets `expiresAt = now + 86400`, rejects later moves/resume with “This mine run expired. Start a new run,” and marks the old run expired on a new start. `ProfileService.php` also omits expired active runs. This is a gameplay deadline, not merely authentication expiry. Remove it with the normal server-run lifecycle; if that lifecycle remains during transition, expiry must not block finishing a puzzle. Preserve unlimited moves, free recovery of unplayable boards, and the beyond-100-moves/elapsed-speed-target regression.
2. **PHP star awards are stale.** The refreshed `backend/tests/town.php` fails with `star formula`. PHP still uses a 1.35 score multiplier and the chest target, while main uses a 1.5 multiplier and authored per-level star targets. Generated content alone does not synchronize the PHP algorithm.
3. **PHP puzzle effects have diverged.** `backend/tests/puzzle.php` fails with `bomb+bomb: jewel collection mismatch` against current JavaScript fixtures. The test stops at the first mismatch, so this is not an exhaustive inventory of drift.

Do not spend the next iteration porting all new game mechanics into PHP only to remove them. The preferred remedy is the requested local-first architecture. Until that replacement lands, the authoritative cloud mode and backend CI are not ready to merge/release.

## What to retain

Retain Symfony, Doctrine/database connectivity, migration/deployment scaffolding, authentication and session protections, ownership checks, request/rate limits, backups, and the explicit public projection/read-only visitor boundary. Both PostgreSQL and MySQL are already supported; select the production database for the actual host rather than treating the old gameplay benchmark as a requirement.

Adapt profile validation to schema/envelope/size checks. Do not validate ordinary saved coins and progression by replaying purchases or maintaining a second game engine. Version compatibility must preserve unsupported/newer saves rather than silently resetting them. Review the existing 64 KiB HTTP body limit against realistic whole-save payloads; the current manual backup parser allows up to 5 MiB, which is not automatically the correct API limit.

Rewrite OpenAPI, hosting/security documentation, CI expectations and the PR title/body around the final local-first implementation. Keep the original authoritative design as historical reference, with clear supersession. Dedicated deterministic challenges and any selective purchase/ad authority remain separate future features; public town viewing does not require them.

## Suggested implementation order

1. Restore local gameplay/persistence as the sole runtime path, migrate local town identity, and retain manual backups. Remove cloud bootstrap and command replacement from game startup.
2. Replace the unused backend schema with accounts, account-owned town records, per-town revisions/history and minimal save APIs. Add safe attachment, concurrent three-slot enforcement and schema validation. Retain reusable authentication/security code without carrying forward game-action tables or a compatibility layer for the undeployed backend.
3. Implement opportunistic sync and conflict UI with independent town state. Cover startup, resume, reconnect, progress saves, account changes, storage reset, network failure and in-flight save races.
4. Finish town management and browser/Capacitor account transport. Test offline-first creation, account-full behavior, duplicate names, rename and explicit deletion on multiple devices.
5. Adapt optional sharing to per-town snapshots, immutable share IDs and EN/FR public-name moderation. Remove ordinary campaign competitive ranking from this milestone.

The multi-town data model should be present from the first save API rather than added after building an account-wide sync mechanism.
