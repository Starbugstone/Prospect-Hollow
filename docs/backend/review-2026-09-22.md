## Architecture

```text
Vue / Phaser / Three.js browser client
              │ same-origin JSON API, cookie + CSRF
              ▼
Apache + PHP 8.4 / Symfony 7.4
  Auth → ProfileService → TownService / PuzzleService / PuzzleEngine
              │ Doctrine DBAL, explicit transactions
              ▼
PostgreSQL 17 (default); MySQL 8.4 also tested
```

Profiles and active boards are JSON records inside relational tables. Sessions, email proofs, action receipts, economy audit entries and public village projections have separate tables. Every mutation locks the owner, checks session/revision, applies server rules and commits its state and receipt together. The browser sends intentions, not replacement saves or claimed rewards. A separate indexed public projection keeps private account data out of visits and leaderboard reads.

The backend uses database-backed sessions and rate limits; there is no Redis dependency or queue worker. Test email goes to Mailpit. Production email is sent synchronously through the configured SMTP provider. JavaScript game definitions are exported into a versioned server catalog during builds. PHP/JavaScript parity tests catch drift.

All **320 measured requests succeeded**. These are warm, early-game, local measurements without TLS or internet latency, not a capacity guarantee. After testing, observed container memory was approximately 190 MiB for PHP/Apache, 84 MiB for PostgreSQL and 22 MiB for Mailpit; these are one-time observations, not sizing limits. PHP OPcache is enabled.

The earlier [database comparison](database-benchmark.md) is more extensive but predates this merge. Its PostgreSQL mining p95 reached about **1.20 seconds at 32 concurrent requests**, and its connection diagnostic found material connection-setup cost. Keep PostgreSQL as the current default; test connection pooling and representative late-game workloads on the intended host before promising scale. No database engine or authentication setting was changed here.

## Security and release work

Verified controls include server-owned rewards and balances, parameterized database calls, atomic spending, session rechecks after locks, exact-origin and CSRF validation, body limits, durable throttling and idempotent retries. HTTPS configurations use Secure/HttpOnly/SameSite=Strict session cookies; local HTTP deliberately uses a development cookie. Login proofs are random, hashed, single-use and expire after 15 minutes. Public listings are opt-in. The packaged server supplies CSP and other security headers.

The implementation has a solid tested foundation; production readiness still needs concrete operational work:

1. Validate real HTTPS/proxy configuration, SMTP delivery and account recovery on the target host.
2. Schedule cleanup and encrypted off-host backups, and perform a restore drill. Scripts and instructions exist; Compose does not schedule these jobs.
3. Add actionable monitoring for errors, latency, disk growth and backup failures. Current unexpected API failures emit only a generic marker, which limits diagnosis.
4. Establish a safe retention/archive design for full action responses, ledgers, old runs and abandoned guests. Current receipts are intentionally retained for retries; storage grows with play.
5. Load-test larger saves and sustained traffic. The application decodes the entire 2.6 MiB content catalog per request and opens database connections per request; measure those costs before optimizing. The web build also flags large rendering chunks (about 6.1 MB for the town chunk before gzip), so initial download speed deserves separate attention.

Packaged Capacitor/native authentication, offline rewarded play and importing editable local saves into cloud accounts remain unsupported. Automated production deployment is disabled. This review does not replace a production security assessment.
